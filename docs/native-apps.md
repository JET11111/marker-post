# Native apps: how the pieces fit

Marker Post is one web app with two thin native shells (Capacitor 8). The web
app is unchanged between the browser and the shells; everything that only a
native app can do lives in one local Capacitor plugin.

```
index.html, app.js, map.js …          the web app (also the GitHub Pages PWA)
platform.js                           the only file that knows it may be inside a native shell
scripts/build-web.mjs                 copies an explicit file list into www/ (pwa or native target)
scripts/build-native-data.mjs         prepares the post data and parity fixtures for Swift and Kotlin
capacitor.config.json                 app id, web dir, plugin settings
android/                              Android shell (generated by Capacitor, committed)
ios/App/                              iOS shell (generated by Capacitor, committed)
ios/App/MarkerPostWidgets/            iOS widget extension: Live Activity + home/lock screen widgets
native/marker-post-plugin/            local Capacitor plugin "marker-post-native"
  package.json, Package.swift         linked into both apps by `npx cap sync`
  ios/Sources/MarkerPostCore/         pure Swift: lookup + types shared with the widget extension
  ios/Sources/MarkerPostNative/       plugin class, background location, Live Activity control
  ios/Tests/MarkerPostCoreTests/      parity tests against the JavaScript answers
  android/                            Kotlin library: plugin, tracking service, notification, widget, lookup, tests
```

Nothing in `www/`, `tiles/` or the generated `posts.tsv` files is committed.
The order on any machine or CI job is always:

```
npm ci
npm run build:native        # www/ for the shells + native data and fixtures
npx cap sync                # copies www/ into both shells and links the plugin
```

## 1. The plugin contract (JavaScript name: `MarkerPost`)

Called from `platform.js` through `Capacitor.registerPlugin('MarkerPost')`.
All methods return promises. Both platforms implement every method.

| Method | Argument | Resolves |
| --- | --- | --- |
| `startTracking` | `{ useHeading: boolean }` | `{ active: true, since: <ms> }` or `{ active: false, reason }` |
| `stopTracking` | none | `{ active: false }` |
| `getTrackingStatus` | none | `{ active: boolean, since?: <ms>, reason?: string }` |
| `updateTracking` | `{ useHeading: boolean }` | `{}` |
| `publishPost` | a snapshot (below, without `stale`/`tracking`) | `{}` |
| `setKeepAwake` | `{ on: boolean }` | `{}` |

Event `trackingChanged` with `{ active: boolean, reason?: string }` fires
whenever tracking starts or stops for any reason (button, notification
action, system).

`reason` is one of: `location-denied`, `location-disabled`,
`location-imprecise`, `activities-disabled` (iOS: Live Activities switched off
for the app), `notifications-denied` (Android), `no-data` (the bundled post
file could not be read), `unsupported`, `stopped-by-user`.

`startTracking` must be called while the app is on screen (both systems only
allow location tracking and Live Activities to begin from the foreground). It
asks for any permission it needs, once, and resolves `{ active: false, reason }`
rather than rejecting when the user says no.

`publishPost` lets the web app hand over the post it is showing while it is in
the foreground, so the widgets have a "last known" value even if live tracking
was never started. It is ignored while tracking is active (the native tracker
is then the single source).

## 2. The snapshot

Every native surface shows one small value object. Its strings are prepared by
JavaScript, never rebuilt natively.

| Field | Meaning |
| --- | --- |
| `road` | display road name: `M27`, `A3(M)`, `Chilworth · M3 / M27` |
| `roadClass` | `M`, `A` or `O`: badge colour only |
| `km` | chainage for display, `17.4`; empty if the recorded reference is unusual (then show `ref`) |
| `letter` | carriageway letter; may be empty |
| `ref` | the recorded reference, verbatim: `P17/4A` |
| `context` | `J4 – J5`, `At J5`, `A303 jct · 349 m`, `Link M27B/M3B`, or empty |
| `confirmed` | carriageway chosen by direction of travel; `false` = by position only |
| `fixTime` | time of the GPS fix (ms since 1970 in JS and Android, `Date` in Swift) |
| `stale` | no usable fix recently: show as last known, not current |
| `tracking` | live tracking was running when this was written |

iOS keeps it as JSON in the App Group `group.io.github.jet11111.markerpost`
(`SharedStore`). Android keeps it as JSON in SharedPreferences
`markerpost_state`, key `snapshot`.

## 3. Data and lookup

`scripts/build-native-data.mjs` writes `posts.tsv` (5,175 posts) and
`nearest-fixtures.tsv` (about 2,000 sampled positions with the JavaScript
answer). The formats are documented at the top of that script.

The native lookup is a direct port of `findNearest` in `core/posts.js`:

```
R = 6371000
toRad(d)      = (d * PI) / 180                      // multiply first, then divide
haversine     : dLat = toRad(lat2 - lat1); dLng = toRad(lng2 - lng1)
                s1 = sin(dLat / 2); s2 = sin(dLng / 2)
                a = s1 * s1 + cos(toRad(lat1)) * cos(toRad(lat2)) * s2 * s2
                return 2 * R * asin(sqrt(a))
angleDiff(a,b)= abs(((a - b + 540) mod 360) - 180)  // mod keeps the sign of the dividend
usable        = useHeading && heading is a number && speed is a number && speed > 2.5

findNearest(lat, lng, heading, speed, useHeading):
  best = none, bestD = +infinity, headingUsed = false
  if usable:
    for each post IN FILE ORDER:
      if post.bearing exists and angleDiff(post.bearing, heading) > 90: skip
      d = haversine(lat, lng, post.lat, post.lng)
      if d < bestD: bestD = d; best = post          // strictly less: the first of equals wins
    headingUsed = best exists and best.bearing exists
  if best is none:
    for each post IN FILE ORDER: same without the skip
  return (index of best, bestD, headingUsed)
```

A heading only exists when the system reports a valid course (0–360) and a
valid speed. iOS reports -1 and Android reports "no bearing" when there is
none; both must become "no heading". Never use the compass.

Tests (Swift: `MarkerPostCoreTests`; Kotlin: JVM unit tests) load both files
and assert, for every fixture: the distance matches within one millionth of a
metre, `headingUsed` matches, and the post index matches whenever the fixture's
`marginM` is above one millionth of a metre (fixtures below that are exact
ties that floating-point libraries may break differently).

## 4. Tracking behaviour (both platforms)

On every fix:

1. Turn course and speed into `heading`/`speed` or "none", as above.
2. `findNearest`.
3. `confirmed` = the heading chose the carriageway, OR the post is on the same
   road and letter as the last heading-confirmed post and the fix is within
   300 m of where that was confirmed. (You cannot change carriageway without
   driving. This affects the label only, never which post is reported.)
4. Build the snapshot (`stale: false`, `tracking: true`).
5. Show it only if something visible changed (`road`, `ref`, `context`,
   `confirmed`, `stale`) and not more than once a second. A heartbeat every
   30 s keeps the "updated" time honest while the post is unchanged.

Stale: a timer checks every 5 s. If the last fix is older than 15 s while the
last known speed was above 2.5 m/s, older than 30 s when speed was unknown, or
older than 120 s when stationary, the snapshot is republished with
`stale: true` and every surface dims and says "No GPS since HH:mm".

The snapshot is also written to the shared store on every visible change, and
the widgets are asked to refresh (iOS: at most every 15 s and on stop;
Android: straight from the service, on every visible change).

Stopping (button, notification action, dismissal) writes a final snapshot with
`tracking: false` and fires `trackingChanged`.

## 5. iOS

Deployment target 18.0 for the app and the extension (set in every build
configuration: the Capacitor CLI reads the first one it finds).

`MarkerTracker` (one shared instance, in `MarkerPostNative`):

- Location: `CLLocationUpdate.liveUpdates(.otherNavigation)` iterated in a
  task, with a `CLBackgroundActivitySession` and, on iOS 18+, a
  `CLServiceSession(authorization: .whenInUse)` held for the whole session.
  Both are created while the app is in the foreground. When-In-Use
  authorisation only; Always is never requested.
- `resumeAfterLaunch()` is called from `AppDelegate` on every launch. If a
  session was active less than 14 hours ago it re-creates the background
  session and resumes the loop; otherwise it clears the flag.
- The lookup runs off the main actor. Fixes are forwarded to the web view only
  while the app is active.
- Live Activity: one `MarkerPostActivityAttributes` activity, `pushType: nil`,
  `staleDate` about 90 s ahead while moving (nil when stationary), relevance
  score = generation.
- The eight-hour limit. iOS ends a Live Activity after 8 hours and a
  background app cannot start another. In order of preference:
  1. iOS 26+: when tracking starts (and whenever the app comes to the front
     with an activity older than 2 hours) the chain is renewed: a fresh
     activity is requested and a successor is scheduled for 7 h 45 min later
     with `Activity.request(…style:alertConfiguration:start:)`. The newest
     active activity receives updates; older ones are ended.
  2. Any iOS: `StartLiveTrackingIntent` (a `LiveActivityIntent`, offered as an
     App Shortcut) restarts the activity without opening the app while the
     location session is still running. It can be run by a Shortcuts
     automation ("When CarPlay connects", "Time of Day").
  3. If no successor exists at 7 h 30 min, one alerting update says the
     display will end at HH:mm and to open Marker Post.
  Untested on a device: see docs/testing-on-device.md.

Widget extension `MarkerPostWidgets` (bundle id `<app id>.widgets`): one
`WidgetBundle` with the Live Activity and the "last known post" widget.

## 6. Android

Everything is in the plugin's library module (Kotlin 2.2.20, no Compose).

- `TrackingService`: foreground service, `foregroundServiceType="location"`,
  started from the visible activity by `startTracking`, `START_NOT_STICKY`.
  Fused Location Provider (high accuracy, 1 s) with the platform GPS provider
  as fallback when Play services is unavailable. Fine location while in use
  only; background location is never requested.
- Ongoing notification: channel importance low, silent, visible on the lock
  screen, one "Stop" action. Swiping it away stops tracking (and the widget
  then says so). On Android 16+ it also asks to be a promoted Live Update with
  the post as its short text.
- Widget: a classic `AppWidgetProvider` with `RemoteViews`, updated directly
  by the service while tracking and by `publishPost` otherwise. Tap opens the
  app.

## 7. What the native surfaces look like

Same visual language as the app (docs: design canvas linked from the README).

- Road badge: motorway `#0B62B8` with white text; A-road `#00693A` with
  `#FFD100` text; anything else a neutral fill with the label colour.
- Post: chainage in the heaviest system weight, tabular digits, tight
  tracking. Carriageway letter in an amber chip (`#FFC23D` on dark surfaces,
  `#FFB81C` on light, text `#1A1200`). Not confirmed: amber outline, amber
  letter, no fill.
- Context line beneath or beside the post.
- Stale: number and context in the secondary text colour, badge and chip at
  55% opacity, and "No GPS since HH:mm".
- Always a time: "Updated HH:mm" on live surfaces, "Last updated HH:mm" on
  widgets. Widgets never claim to be live.
- No controls on anything shown while driving, except "Stop" in the Android
  notification.

## 8. What cannot be checked without a device

CI compiles both apps, runs the parity tests, and builds the widget extension
for the simulator. It cannot show that a Live Activity appears on a CarPlay
screen, that iOS keeps delivering location for twelve hours, or how an
Android phone's battery settings treat the service. Those are listed, with
exact steps, in docs/testing-on-device.md.
