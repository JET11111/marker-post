# Native apps: how the pieces fit

Marker Post is one web app with two thin native shells (Capacitor 8). The web
app is unchanged between the browser and the shells; everything that only a
native app can do lives in one local Capacitor plugin.

```
index.html, app.js, map.js …          the web app (also the GitHub Pages PWA)
platform.js                           the only file that knows it may be inside a native shell
scripts/build-web.mjs                 copies an explicit file list into www/ (web app) or www-native/ (phone apps)
scripts/build-native-data.mjs         prepares the post data and parity fixtures for Swift and Kotlin
capacitor.config.json                 app id, web dir, plugin settings
android/                              Android shell (generated by Capacitor, committed)
ios/App/                              iOS shell (generated by Capacitor, committed)
ios/App/MarkerPostWidgets/            iOS widget extension: Live Activity + home/lock screen widgets
native/marker-post-plugin/            local Capacitor plugin "marker-post-native"
  package.json, Package.swift         linked into both apps by `npx cap sync`
  ios/Sources/MarkerPostCore/         pure Swift: lookup + types shared with the widget extension
  ios/Sources/MarkerPostNative/       plugin class, background location, Live Activity control
  ios/Tests/MarkerPostCoreTests/      parity tests against the JavaScript answers, tracking rules, wording
  android/                            Kotlin library: plugin, tracking service, notification, widget, lookup, tests
```

Nothing in `www/`, `www-native/`, `tiles/` or the generated `posts.tsv` files is committed.
The order on any machine or CI job is always:

```
npm ci
npm run build:native        # www-native/ for the shells + native data and fixtures
npx cap sync                # copies www-native/ into both shells and links the plugin
```

If `npx cap sync` says it could not find the web assets directory, run
`npm run build:native` first (not `npm run build`, which makes the web app in `www/`).

## 1. The plugin contract (JavaScript name: `MarkerPost`)

Called from `platform.js` through `Capacitor.registerPlugin('MarkerPost')`.
All methods return promises. Both platforms implement every method.

| Method | Argument | Resolves |
| --- | --- | --- |
| `startTracking` | `{ useHeading: boolean }` | `{ active: true, since: <ms>, reason? }` or `{ active: false, reason? }` |
| `stopTracking` | none | `{ active: false }` |
| `getTrackingStatus` | none | `{ active: boolean, since?: <ms>, reason?: string }` |
| `updateTracking` | `{ useHeading: boolean }` | `{}` |
| `publishPost` | a snapshot (below, without `stale`/`tracking`) | `{}` |
| `setKeepAwake` | `{ on: boolean }` | `{}` |

`reason` is one of: `location-denied`, `location-disabled`,
`location-imprecise`, `activities-disabled` (iOS: Live Activities switched off
for the app), `notifications-denied` (Android), `no-data` (the bundled post
file could not be read), `unsupported`, `stopped-by-user`.

- A start that succeeded can still carry a reason. On Android,
  `notifications-denied` means tracking runs but its notification cannot be
  shown (notifications are off for the app, or only for its "Live tracking"
  category), so the post is nowhere to be seen. The app says so.
- iOS gives no `reason` when it would not start the Live Activity and none of
  these words fits (usually a passing cause, such as the app not being on
  screen yet). The app then says only that live tracking could not start.
  On iPhone `unsupported` now means only that the system has no Live
  Activities at all.
- A second `startTracking` that arrives while one is still in progress waits
  for it and resolves with the same answer.
- While tracking is on, `getTrackingStatus` on iOS gives the present location
  problem as `reason` (`location-disabled`, `location-denied`,
  `location-imprecise`), if there is one.

Event `trackingChanged` with `{ active: boolean, reason?: string }` fires
whenever tracking starts or stops while the app is running (button,
notification action, system). iOS fires nothing at launch, whether a session is
carried on there or ended there: the app reads `getTrackingStatus` when it
starts. iOS also fires `trackingFix` with the whole snapshot for each fix it
uses, while the app is on screen; the web app does not listen to it.

`startTracking` must be called while the app is on screen (both systems only
allow location tracking and Live Activities to begin from the foreground). It
asks for any permission it needs, once, and resolves `{ active: false, reason }`
rather than rejecting when the user says no.

`publishPost` lets the web app hand over the post it is showing while it is in
the foreground, so the widgets have a "last known" value even if live tracking
was never started. It is ignored while tracking is active (the native tracker
is then the single source).

## 2. The snapshot

Every native surface shows one small value object. Its strings are prepared by
JavaScript, never rebuilt natively.

| Field | Meaning |
| --- | --- |
| `road` | display road name: `M27`, `A3(M)`, `Chilworth · M3 / M27` |
| `roadClass` | `M`, `A` or `O`: badge colour only |
| `km` | chainage for display, `17.4`; empty if the recorded reference is unusual (then show `ref`) |
| `letter` | carriageway letter; may be empty |
| `ref` | the recorded reference, verbatim: `P17/4A` |
| `context` | the line under the post: `J4 – J5`, `Within J5`, `A303 jct · 1.24 km from post`, `Link M27B/M3B · survey date unknown`, or empty; or `Nearest recorded post · 1.24 km away` when the post is more than 250 m from the fix (section 4). Up to 37 characters. It describes the post, never the vehicle. |
| `confirmed` | carriageway chosen by direction of travel; `false` = by position only |
| `fixTime` | time the position was true (ms since 1970 in JS and Android, `Date` in Swift) |
| `stale` | no usable fix recently: show as last known, not current |
| `tracking` | live tracking was running when this was written |

Two things the phone surfaces leave out, by decision (23 November 2026):

- **The far line replaces the post's own line.** On an interchange link post
  that line ends "survey date unknown", and the far line has no room for it. It
  already says the post is only the nearest on record, a long way off. The
  app's first page keeps both.
- **Distances in the line are straight-line.** "A303 jct · 1.24 km from post"
  is measured in a straight line from the post to the junction, and the far
  line's distance in a straight line from the fix. The app's first page says
  "distances are straight-line"; the phone surfaces have no room and print the
  line as it is.

iOS keeps it as JSON in the App Group `group.io.github.jet11111.markerpost`
(`SharedStore`). Android keeps it as JSON in SharedPreferences
`markerpost_state`, key `snapshot`.

## 3. Data and lookup

`scripts/build-native-data.mjs` writes `posts.tsv` (5,175 posts) and
`nearest-fixtures.tsv` (about 2,000 sampled positions with the JavaScript
answer). The formats are documented at the top of that script.

The native lookup is a direct port of `findNearest` in `core/posts.js`:

```
R = 6371000
toRad(d)      = (d * PI) / 180                      // multiply first, then divide
haversine     : dLat = toRad(lat2 - lat1); dLng = toRad(lng2 - lng1)
                s1 = sin(dLat / 2); s2 = sin(dLng / 2)
                a = (s1 * s1) + (cos(toRad(lat1)) * cos(toRad(lat2))) * (s2 * s2)   // the squares first, as written here
                return 2 * R * asin(sqrt(a))
angleDiff(a,b)= abs(((a - b + 540) mod 360) - 180)  // mod keeps the sign of the dividend
usable        = useHeading && heading is a number && speed is a number && speed > 2.5

findNearest(lat, lng, heading, speed, useHeading):
  best = none, bestD = +infinity, headingUsed = false
  if usable:
    for each post IN FILE ORDER:
      if post.bearing exists and angleDiff(post.bearing, heading) > 90: skip
      d = haversine(lat, lng, post.lat, post.lng)
      if d < bestD: bestD = d; best = post          // strictly less: the first of equals wins
    headingUsed = best exists and best.bearing exists
  if best is none:
    for each post IN FILE ORDER: same without the skip
  return (index of best, bestD, headingUsed)
```

A heading only exists when the system reports a valid course (0–360) and a
valid speed. iOS reports -1 and Android reports "no bearing" when there is
none; both must become "no heading". Never use the compass.

Tests (Swift: `MarkerPostCoreTests`; Kotlin: JVM unit tests) load both files
and assert, for every fixture: the distance matches within one millionth of a
metre, `headingUsed` matches, and the post index matches whenever the fixture's
`marginM` is above one millionth of a metre (a margin below that would be an
exact tie between posts in different places, which two maths libraries may
break differently; the data has none today. Two posts recorded at the very
same point are not such a tie: the heading and then file order decide, and the
tests hold the lookups to the recorded post).

## 4. Tracking behaviour (both platforms)

On every fix:

1. **Too rough is not a position.** A fix whose reported accuracy is worse
   than 100 m (the posts are 100 m apart) is ignored: it does not move the
   post, and it does not refresh the "updated" time or the stale clock. A fix
   with no accuracy figure is accepted. On iPhone a negative accuracy is Core
   Location's "not a position" and is turned away first; a fix turned away for
   being rough still clears the problem words, because positions are arriving
   again, but a post they dimmed stays dimmed.
2. **The time of a fix is when the position was true**, not when it arrived:
   on Android now minus the fix's age by the monotonic clock, on iPhone the
   location's own timestamp; never in the future. A fix older than the one
   already shown is ignored. A fix already past its limit (below) when it
   arrives is stale from the start.
3. Turn course and speed into `heading`/`speed` or "none", as above.
4. `findNearest`.
5. **Far from any recorded post.** A post more than 250 m from the fix
   (straight-line) is never confirmed, and its line is the far line:
   `Nearest recorded post · <distance> away`, the distance written exactly as
   the web app's `fmtDist` writes it ("38 m", "1.24 km", "12.4 km"; a full
   stop whatever the phone's language). Such a fix neither makes nor forgets a
   confirmation. Nothing else changes, and nothing says the vehicle is off the
   road.
6. `confirmed` = the heading chose the carriageway, OR the post is on the same
   road and letter as the last heading-confirmed post and the fix is within
   300 m of where that was confirmed. (You cannot change carriageway without
   driving. This affects the label only, never which post is reported.)
   The phone trackers keep a confirmation across a gap in fixes; the web app
   forgets it after 15 s without a fix (`CONFIRM_GAP_MS` in `core/posts.js`).
   That difference is by decision (23 November 2026): a straight port is wrong
   for iPhone, where every stop while parked is such a gap and Core Location's
   own pause says the phone did not move, and the 300 m bound still applies.
7. Build the snapshot (`stale: false`, `tracking: true`).
8. Show it only if something visible changed (`road`, `ref`, `context`,
   `confirmed`, `stale`) and not more than once a second. A change that is only
   the distance in the far line is shown at most every 5 s. A heartbeat every
   30 s keeps the "updated" time honest while the post is unchanged. iOS: while
   Core Location has paused its updates the display is sent again every 10
   minutes, and the start of a pause is sent at once. Everything is sent once
   after midnight, so a time from yesterday gains its date.

**Stale.** A timer checks every 5 s. The limit is the web app's
`staleAfterMs(speed)`: 15 s when the last known speed was above 2.5 m/s, 120 s
when it was at or below 2.5 m/s, and 30 s when the speed is unknown (a speed
that is not a number counts as unknown). Past it, the snapshot is republished
with `stale: true` and every surface dims and says "No GPS since 14:32".

- iOS: when Core Location says it has no position, or that Location Services,
  the permission, Precise Location or "in use" has been lost, the post is
  marked stale at once. The Live Activity says why ("Location Services are
  off", "Location permission needed", "Precise Location is off", "Open Marker
  Post to resume"); "No GPS signal" is shown only when there is no post to dim.
- iOS pause: Core Location stops sending positions once it judges the phone
  has stopped moving, and says so. A fix taken at 2.5 m/s or less (or with no
  speed) that was no more than 15 s old when the pause began, or that arrives
  during it, stays current while the pause lasts. Every other fix follows the
  rule above.

The snapshot is also written to the shared store on every visible change, and
the widgets are asked to refresh (iOS: at most every 15 s and on stop;
Android: straight from the service, on every visible change).

**Stopping** (button, notification action, dismissal) writes a final snapshot
with `tracking: false` and fires `trackingChanged`. If this run of the app has
not found a post yet, the `tracking` mark is taken off the post already in the
shared store instead. iOS: a session also ends by itself 14 hours after it
started (no reason), when its Live Activity is swiped away (`stopped-by-user`),
and when Live Activities are switched off for the app (`activities-disabled`).
A session ended at launch fires no event; the app reads `getTrackingStatus`.

## 5. iOS

Deployment target 18.0 for the app and the extension (set in every build
configuration: the Capacitor CLI reads the first one it finds).

`MarkerTracker` (one shared instance, in `MarkerPostNative`):

- Location: `CLLocationUpdate.liveUpdates(.otherNavigation)` iterated in a
  task, with a `CLBackgroundActivitySession` and, on iOS 18+, a
  `CLServiceSession(authorization: .whenInUse)` held for the whole session.
  Both are created while the app is in the foreground. When-In-Use
  authorisation only; Always is never requested.
- `resumeAfterLaunch()` is called from `AppDelegate` on every launch. A session
  started less than 14 hours ago is carried on if its Live Activity is still on
  screen, or if nothing is on screen but the display had reached the last five
  minutes of its eight hours (or its follow-on was due within a minute). It is
  also carried on when the app has no record of when the display was due to
  end: a session begun by an earlier version, or one whose nearly-over display
  the shortcut ended for a second request that iOS also refused. The first
  position waits for the post list. If the Live Activity went before its time,
  it was swiped away while the app was not running: the session is ended
  there, location is not started, no event is fired, and `getTrackingStatus`
  gives `stopped-by-user` (`activities-disabled` when Live Activities are off).
  With no session to carry on, launch removes any Live Activity, and any
  follow-on still waiting, left behind.
- The lookup runs off the main actor. Fixes are forwarded to the web view only
  while the app is active.
- Live Activity: one `MarkerPostActivityAttributes` activity, `pushType: nil`,
  `staleDate` 90 s ahead for a post shown as current, or 30 minutes while the
  pause accounts for the silence; never nil for a post shown as current.
  Relevance score = generation. The state of each activity is followed through
  `activityStateUpdates` as well as `activityState`; whichever is further along
  counts.
- The eight-hour limit. iOS ends a Live Activity after 8 hours and a
  background app cannot start another. In order of preference:
  1. iOS 26+: when tracking starts (and whenever the app comes to the front
     with an activity older than 2 hours) the chain is renewed: a fresh
     activity is requested and a successor is scheduled for 7 h 45 min later
     with `Activity.request(…style:alertConfiguration:start:)`. The newest
     active activity receives updates; older ones are ended. A request iOS
     refuses leaves the display as it is. The old activities are ended for a
     second try only when iOS says there are too many Live Activities, or when
     the shortcut asks and there is next to nothing to lose: no follow-on is
     waiting, and either nothing is showing or the display has had its
     7 h 30 min warning. After its own request is refused the app waits a
     minute before asking again; a refusal of the shortcut's request sets no
     wait, so opening the app afterwards renews at once.
  2. Any iOS: `StartLiveTrackingIntent` (a `LiveActivityIntent`, offered as an
     App Shortcut, "Show nearest marker post"; to Siri, "Show Marker Post")
     restarts the activity without opening
     the app while the location session is still running. It can be run by a
     Shortcuts automation ("When CarPlay connects", "Time of Day"). It never
     starts tracking or location, and waits for a renewal already under way.
     It always says what happened:
     - "The marker post display has been renewed."
     - "The marker post display is still on. It could not be renewed." iOS
       refused, and the display that was there, or its follow-on, is still on
       screen. Siri is reported to refuse while another activity of the app is
       showing, so this may be the usual answer by voice.
     - "The marker post display could not be renewed. Open Marker Post." iOS
       refused and nothing is on screen.
     - "Live tracking is off. Open Marker Post to start it."
  3. If no successor exists at 7 h 30 min, one alerting update says the
     display will end at HH:mm and to open Marker Post.

  Known limit: on iOS 26 a follow-on already scheduled still starts if the
  display was swiped away while the app was not running and the app is not
  opened before then. Opened after that, within 14 hours of the start, the app
  finds a Live Activity on screen and carries the session on.

  Untested on a device: see docs/testing-on-device.md.

Widget extension `MarkerPostWidgets` (bundle id `<app id>.widgets`): one
`WidgetBundle` with the Live Activity and the "Last known marker post" widget.

## 6. Android

Everything is in the plugin's library module (Kotlin 2.2.20, no Compose).

- `TrackingService`: foreground service, `foregroundServiceType="location"`,
  started from the visible activity by `startTracking`, `START_NOT_STICKY`.
  Fused Location Provider (high accuracy, 1 s) with the platform GPS provider
  as fallback when Play services is unavailable. Fine location while in use
  only; background location is never requested.
- Ongoing notification: channel importance low, silent, visible on the lock
  screen, one "Stop" action. Swiping it away stops tracking (the widget keeps
  the last post and its time).
  - Title: the post on one line, "M27 17.4 A". Far from a post (section 4,
    step 5) a letter that is not confirmed is left out: "M3 117.4".
  - Text, in this order, so that a lock screen that shows one line cuts the
    least important part: the time ("Updated 14:32", or "No GPS since 14:32"
    when stale); far from a post, the far line; "Check carriageway" when the
    letter is not confirmed; "last known post" when stale; then the line under
    the post. For example "Updated 14:32 · Check carriageway · J4 – J5", and
    "Updated 14:32 · Nearest recorded post · 1.24 km away · Check carriageway".
  - On Android 16+ it also asks to be a promoted Live Update. Its short text
    (the status bar chip) is the post, "17.4A", or "17.4" when the letter is
    not confirmed. There is no chip when the post is stale, far from the fix,
    or longer than six characters: the chip has no room to say so.
- Widget: a classic `AppWidgetProvider` with `RemoteViews`, updated directly
  by the service while tracking and by `publishPost` otherwise, and when the
  launcher gives it a new size. Its time line is "Last updated 14:32", or "No
  GPS since 14:32" when the position is stale, and may take up to three lines
  (it is never the part cut). The line under the post takes two lines only
  where the widget is tall enough at the phone's text size, otherwise one, cut
  at its end. Each drawing books one redraw for the next midnight, so a time
  from yesterday gains its date. It never says "Live". Tap opens the app.
- Debug builds only: a screen that draws the widget in each of its states
  (`src/debug`, `WidgetPreviewActivity`), which the emulator check photographs
  and measures. It is not in the release build.

## 7. What the native surfaces look like

Same visual language as the app (docs: design canvas linked from the README).

- Road badge: motorway `#0B62B8` with white text; A-road `#00693A` with
  `#FFD100` text; anything else a neutral fill with the label colour.
- Post: chainage in the heaviest system weight, tabular digits, tight
  tracking. Carriageway letter in an amber chip (`#FFC23D` on dark surfaces,
  `#FFB81C` on light, text `#1A1200`). Not confirmed: amber outline, amber
  letter, no fill. Where a surface can only print text it leaves a letter that
  is not confirmed out, or says "Check carriageway" in words: never a plain
  letter that looks the same as a confirmed one. Screen readers hear it too.
- Context line beneath or beside the post. Surfaces give it room (two lines
  where they can) or cut it at its end with an ellipsis. They never shorten it
  themselves, and never cut the time to make room for it.
- Stale: number and context in the secondary text colour, badge and chip at
  55% opacity, and "No GPS since 14:32", in words or, where there is no room
  for words, a symbol.
- Always a time, and the time is never the part that gets cut: where a line
  can be shortened by the system, the time comes first. "Updated 14:32" on
  live surfaces, "Last updated 14:32" on widgets. Widgets never claim to be
  live.
- Times are 24-hour on every surface, whatever the phone's own setting. A time
  that is not from today carries its day ("21 Nov, 14:32"), and its year when
  that is not this year. A surface that can sit unchanged overnight redraws
  after midnight so that it does.
- At night the colours are the app's navy, not black and grey: background
  `#0A0F1A`, surface `#121B2E`, fill `#1B2740`, text `#F3F6FB`, secondary text
  `#8595AC`. iPhone widgets on the Home Screen follow the system's own widget
  rendering modes; where the widget supplies its own colours, they are these.
- No controls on anything shown while driving, except "Stop" in the Android
  notification.

## 8. App links

Both apps answer links that begin `markerpost://`. They are handled by the web
code (`onAppLink` in platform.js, wired in app.js), so both platforms behave the
same way:

| Link | What it does |
|---|---|
| `markerpost://nearest`, `markerpost://map`, `markerpost://signs`, `markerpost://goto` | opens the app on that screen |
| `markerpost://live/start` | opens the app and starts live tracking, if it is not already running |
| `markerpost://live/stop` | stops live tracking |

They exist for two reasons. A phone automation can use `markerpost://live/start`
to start tracking when the phone connects to the vehicle (iOS: Shortcuts,
Automation, CarPlay, Connects, Open URLs; iOS may ask you to unlock the phone
first, because a Live Activity can only be started by an app that is on screen).
And the automated checks on GitHub use them to drive the app in a simulator and
an emulator, where nothing can press a button.

A link can only do what the buttons in the app do. Unknown links just open the app.

Opening a link from a real automation app has not been tried on a phone yet. It
is on the list in docs/testing-on-device.md (steps C8 and F9).

## 9. What cannot be checked without a device

CI compiles both apps, runs the parity, tracking-rule and wording tests, and
builds the widget extension for the simulator. The Android emulator check also
drives a simulated M27 journey and photographs the widget preview by day, by
night and with large text. CI cannot show that a Live Activity appears on a
CarPlay screen, that iOS keeps delivering location for twelve hours, or how an
Android phone's battery settings treat the service. Those are listed, with
exact steps, in docs/testing-on-device.md.
